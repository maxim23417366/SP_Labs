# Специфікація метрик, форматів логів та шаблонів результатів (SmartLock — ЛР3, ЛР4)

## 1. Апаратна та системна база вимірювань

* **Мікроконтролер:** STM32F411RET6 (NUCLEO-F411RE)
* **Тактування:** `SYSCLK = 96 МГц` (HSE 8 МГц bypass), `APB1 = 48 МГц`, `APB2 = 96 МГц`
* **Ресурси пам'яті:** `FLASH = 512 КБ`, `RAM = 128 КБ`
* **Дискретність лічильника циклів `DWT->CYCCNT`:** 1 такт = $\approx 10.42\text{ нс}$ (період переповнення 32-бітного лічильника при 96 МГц становить $\approx 44.74\text{ с}$)
* **Інтерфейс виводу діагностики:** `USART2` (`PA2/PA3`, `115200 8N1`) через ST-LINK VCP / YP-05
* **Комбіновані методи вимірювання:**
  1. Програмні лічильники тактів ядра (`DWT`) для внутрішніх часових інтервалів.
  2. Подієві логи з мітками часу мікроконтролера (`EVT`) для довгих ланцюжків операцій.
  3. Службові піни `GPIO` + логічний аналізатор (PulseView) для зовнішньої апаратної верифікації.
  4. Звіти компілятора/лінкера (`--print-memory-usage`, `.map`, `.su`) та *stack painting* (`0xDEADBEEF`) для контролю пам'яті.

## 2. Перелік вимірюваних метрик

| Код метрики | Назва метрики | Одиниці / Формат | Що саме вимірюється в SmartLock | Спосіб виміру |
| :--- | :--- | :--- | :--- | :--- |
| **M-01** | Час виконання задачі ($T_{\text{task}}$) | `min / avg / max` (мкс) | Тривалість runtime-задач Super Loop за `docs/tasks.md`: `fsm`, `buttons`, `security` (MPU-6050, PIR, геркон), `env` (DHT11, BMP180), `camera` (OV7670), `storage` (W25Q64), `uart`. У поточному каркасі `camera` ще не зареєстрована у `app_tasks.c`, тому її статистика з’явиться після інтеграції | `DWT` + службові GPIO |
| **M-02** | Період головного циклу ($T_{\text{loop}}$) | `min / avg / max` (мкс) | Повний час однієї ітерації `while(1)` у холостому та навантаженому режимах | `DWT` |
| **M-03** | Затримка реакції на подію ($L_{\text{event}}$) | `min / avg / max / p99` (мкс) | Час від виникнення події до початку реакції в циклі: кнопка блокування (`PC13`), кодові кнопки (`PA1/4/7/9`), `PIR` (`PA0`), геркон (`PB4`), прийом команди UART | `DWT` (мітка ISR або polling $\rightarrow$ обробка) + логічний аналізатор |
| **M-04** | Джитер періодичних задач ($J_{\text{task}}$) | `min / max` відхилення (мкс), гістограма | Відхилення реального інтервалу запуску періодичних задач (`buttons`, `security`, `env`) від заданого періоду $T_{\text{nom}}$ та кількість пропущених запусків (`dt > 2 * T_nom` у `sched.c`) | `DWT` |
| **M-05** | Завантаження CPU ($U_{\text{CPU}}$) | `%` (вікно 1000 мс; у `sched.c` статистика `cpu_load_pm` у проміле, для % ділити на 10) | Частка часу за секунду, коли задачі виконували реальну роботу (без урахування порожніх перевірок таймерів) | `DWT` |
| **M-06** | Статична пам'ять Flash та RAM | Байти та `%` | Загальне заповнення `FLASH` і `RAM`, розбивка за секціями (`.text`, `.data`, `.bss`), модулями (`*.o`) та найбільшими символами | `-Wl,--print-memory-usage`, `arm-none-eabi-size`, `nm` |
| **M-07** | Використання стека (Static & Peak) | Байти / Запас (байт) | Статичний розмір кадрів функцій (`.su`) та фактичний максимум заповнення стека під час сценарію S3 | `-fstack-usage` + *Stack Painting* (`0xDEADBEEF`) |
| **M-08** | Використання динамічної пам'яті (Heap) | `arena / used / free` (байт) | Пікове виділення та перевірка відсутності витоків після тривалої роботи (якщо використовується `malloc`) | `mallinfo()` |

## 3. Протокол форматів UART-логів (контракт для парсингу)

Усі діагностичні рядки повинні починатися з фіксованого префікса великими літерами та завершуватися `\r\n`. Час прибуття рядка на ПК **не використовується** через буферизацію USB VCP — усі часові мітки формуються всередині STM32. Формати `STAT`/`EVT`/`JITTER`/`LOAD`/`MEM` нижче — цільовий контракт для реалізації вимірювань і парсера; у поточному каркасі ще не всі ці рядки реалізовані.

### 3.1. Банер версії збірки (на старті системи)
Фіксує точний коміт прошивки для прив'язки логів до бінарного файлу:
```text
BUILD,fw=SmartLock,lab=LR3,git=<short_hash>,cpu_hz=96000000,loop=superloop
```
*Приклад:* `BUILD,fw=SmartLock,lab=LR3,git=a1b2c3d,cpu_hz=96000000,loop=superloop`

У ЛР4: `lab=LR4`, `loop=freertos` — так логи ЛР3 і ЛР4 не переплутати.

### 3.2. Статистика часу виконання задач та затримок (`STAT`)
Виводиться за командою `STATS` або після завершення тестового прогону:
```text
STAT name=<task_or_latency_name> n=<count> min_us=<min> avg_us=<avg> max_us=<max>
```
*Приклади:*
```text
STAT name=loop n=45210 min_us=42 avg_us=68 max_us=98400
STAT name=security n=9000 min_us=210 avg_us=235 max_us=640
STAT name=camera n=15 min_us=33100 avg_us=33450 max_us=34200
STAT name=flash_erase n=5 min_us=45200 avg_us=51000 max_us=68400
STAT name=btn_b1_lat n=40 min_us=18 avg_us=410 max_us=96500
```
*Регулярний вираз для парсингу:* `^STAT name=(\S+) n=(\d+) min_us=(\d+) avg_us=(\d+) max_us=(\d+)$`

### 3.3. Подієві мітки часу (`EVT`)
Використовуються для вимірювання затримок у багатоетапних сценаріях (час `t_us` — безперервний 64-бітний лічильник мікросекунд на базі `DWT` або апаратного таймера 1 МГц):
```text
EVT t_us=<timestamp_us> name=<event_name>
```
*Стандартні імена подій SmartLock:*
* `btn_b1_press` $\rightarrow$ `btn_b1_handled` (реакція на блокування/розблокування)
* `code_key_press` $\rightarrow$ `code_key_handled` (введення коду доступу)
* `pir_trig` $\rightarrow$ `alarm_triggered` (спрацювання датчика руху HC-SR501)
* `capture_start` $\rightarrow$ `capture_done` (захоплення кадру OV7670)
* `flash_wr_start` $\rightarrow$ `flash_wr_done` (запис журналу або кадру у W25Q64)
* `uart_cmd_rx` $\rightarrow$ `uart_cmd_tx` (обробка вхідної команди)

*Приклад:*
```text
EVT t_us=10234567 name=btn_b1_press
EVT t_us=10234610 name=btn_b1_handled
EVT t_us=10235000 name=capture_start
EVT t_us=10268420 name=capture_done
```
*Регулярний вираз для парсингу:* `^EVT t_us=(\d+) name=(\S+)$`

*Примітка:* рядки журналу подій (`EVT,id=<seq>,t_ms=...,name=<ТИП>,...,flash=ok|err`, `App/sl_journal.c`, FR-12) мають той самий префікс, але після `EVT` — кома, а не пробіл: це не мітки часу, регулярний вираз вище їх не захоплює. Парсер має відбирати рядки за повним виразом, а не за префіксом `EVT`.

### 3.4. Джитер періодичних задач (`JITTER`)
```text
JITTER name=<task_name> period_us=<nom> min_us=<min_err> max_us=<max_err> missed=<cnt>
```
*Приклад:* `JITTER name=security period_us=20000 min_us=-12 max_us=93400 missed=18`

### 3.5. Завантаження процесора (`LOAD`)
Виводиться раз на секунду:
```text
LOAD pct=<0..100>
```
*Приклад:* `LOAD pct=14`

### 3.6. Звіт про використання стека та heap (`MEM`)
Виводиться за командою `MEM` до та після виконання тестового сценарію:
```text
STACK reserved=<bytes> used=<bytes> free=<bytes>
HEAP arena=<bytes> used=<bytes> free=<bytes>
```
*Приклад:*
```text
STACK reserved=2048 used=1384 free=664
HEAP arena=0 used=0 free=0
```

### 3.7. Нові рядки ЛР4 (FreeRTOS)

Рядки §3.1–3.6 у ЛР4 лишаються без змін і з тими самими іменами подій. Нові рядки ЛР4 лише
додаються до них. Їх розбирає `scripts/parse_uart_logs.py` (M03). Формати погоджено в рев'ю
K01 (`docs/rtos-design.md`, PR #68).

**Стек кожної задачі** — за командою `MEM`, один рядок на задачу, у байтах (із
`uxTaskGetStackHighWaterMark` × 4). Стек переривань (MSP, `_Min_Stack_Size` = 4 096 Б) — рядок з `task=MSP`:
```text
STACK task=<ім'я задачі> reserved=<bytes> used=<bytes> free=<bytes>
```
*Приклад:*
```text
STACK task=buttons reserved=640 used=212 free=428
STACK task=MSP reserved=4096 used=520 free=3576
```
*Регулярний вираз:* `^STACK task=(\S+) reserved=(\d+) used=(\d+) free=(\d+)$`.
Допустимий скорочений варіант (лише high water mark у словах): `STACK task=<ім'я> free_min_words=<слова>`.
Рядок `STACK reserved=…` без `task=` (§3.6) — це стек ЛР3. Сума стеків задач рахується без `MSP`.

**Heap FreeRTOS** — за командою `MEM`, з `xPortGetFreeHeapSize()` і `xPortGetMinimumEverFreeHeapSize()`.
Рядок newlib `HEAP arena=…` (§3.6) лишається поряд, тому heap ОС має інший префікс:
```text
OSHEAP free=<bytes> min_ever_free=<bytes> total=<configTOTAL_HEAP_SIZE>
```
*Приклад:* `OSHEAP free=9216 min_ever_free=8704 total=20480` → пік використання = `total − min_ever_free`.
*Регулярний вираз:* `^OSHEAP free=(\d+) min_ever_free=(\d+) total=(\d+)$` (парсер приймає й префікс `HEAP free=`).

**Час CPU по задачах** (run-time stats) — за командою `STATS`, блок між `TASKS_BEGIN` і `TASKS_END`:
```text
TASKS_BEGIN total=<загальний час лічильника>
TASK name=<ім'я> prio=<пріоритет> runtime=<ticks> pct=<0..100>
TASKS_END
```
*Приклад:*
```text
TASKS_BEGIN total=60000000
TASK name=IDLE prio=0 runtime=52800000 pct=88
TASK name=security prio=5 runtime=2400000 pct=4
TASK name=camera prio=1 runtime=4800000 pct=8
TASKS_END
```
Блок містить усі задачі, і `IDLE` теж. Сума `runtime` дорівнює `total`.
*Регулярний вираз:* `^TASK name=(\S+)(?: prio=(\d+))? runtime=(\d+) pct=(<?\d+(?:\.\d+)?)%?$`.
Усередині блоку дозволено й сирий вивід `vTaskGetRunTimeStats` (`ім'я<таб>час<таб>відсоток%`,
`<1%` → 0,5 %). Пробіл в імені (`Tmr Svc`) парсер замінює на `_`.

**Завантаження CPU у ЛР4 (M-05)** друкується двома способами:
* `LOAD pct=` (§3.5) рахується так само, як у ЛР3: сума тривалостей задач за вікно 1 с;
* у звіті парсера — `100 − частка IDLE` з блоку `TASKS` (рахується за `runtime`). У прикладі вище це 12 %.

У порівнянні з ЛР3 використовують перший спосіб, а другий наводять для довідки.

**Трасування перемикань** (`traceTASK_SWITCHED_IN`) — необов'язкове, між `TRACE_BEGIN` і `TRACE_END`:
```text
TRACE t_us=<64-бітний час DWT> task=<ім'я>
```
*Регулярний вираз:* `^TRACE t_us=(\d+) task=(\S+)$`.

**Паритет вимірювань.** Під час S1–S3 трасування й автоматичний вивід `TASKS` вимкнені прапорцем
збірки. Їх вмикають лише в окремих прогонах, щоб друк не додавав навантаження, якого не було в ЛР3.

**Імена `STAT` у ЛР3 і ЛР4.** `STAT name=<задача>` друкується з іменами задач FreeRTOS. Для
порівняння парсер зіставляє імена ЛР3 так: `uart` → `cmd` + `logger`, `mem` → `logger`,
`loop` → немає відповідника (у ЛР4 немає головного циклу). Решта імен збігаються.

## 4. Сценарії тестування для збору метрик

Усі вимірювання виконуються на одній і тій самій збірці прошивки (однаковий `git` у банері `BUILD` та частота UART):

1. **S1 — Простій (Idle):** Система увімкнена, подій доступу немає, камера та запис у Flash неактивні, працюють лише базові періодичні опитування та фоновий цикл.
2. **S2 — Номінальний режим (PRD):** Типова робота замка згідно з вимогами PRD: регулярне опитування сенсорів (MPU-6050, DHT11, BMP180, геркон), поодинокі натискання кнопок/спрацювання PIR, періодичний запис подій у журнал W25Q64.
3. **S3 — Найгірший випадок (Worst-case):** Одночасне накладання всіх важких операцій: захоплення кадру з OV7670 + стирання сектора / запис у W25Q64 + безперервний потік команд по UART + серія зовнішніх подій (натискання кнопки `PC13` / спрацювання `PIR` щонайменше 30–50 разів у випадкові моменти).
4. **Додаткові стрес-сценарії (п. 6.2 методички):**
   * Відмова пристрою на шині I2C1 (від'єднання сенсора або замикання SDA на GND) — вимірювання часу блокування на `Timeout`.
   * Потік команд по UART без пауз під час захоплення кадру — підрахунок втрачених байтів (`ORE` / переповнення кільцевого буфера).
   * Пошук точки зламу — підвищення частоти опитування сенсорів / частоти команд до порушення дедлайнів PRD.
   * Тривалий прогін у режимі S2 (від 60 хв) — перевірка переповнення 32-бітного `DWT` (кожні ~44.74 с) та стабільності пам'яті.
