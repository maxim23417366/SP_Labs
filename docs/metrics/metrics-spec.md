# Специфікація метрик, форматів логів та шаблонів результатів (SmartLock — ЛР3)

## 1. Апаратна та системна база вимірювань

* **Мікроконтролер:** STM32F411RET6 (NUCLEO-F411RE)
* **Тактування:** `SYSCLK = 96 МГц` (HSE 8 МГц bypass), `APB1 = 48 МГц`, `APB2 = 96 МГц`
* **Ресурси пам'яті:** `FLASH = 512 КБ`, `RAM = 96 КБ`
* **Дискретність лічильника циклів `DWT->CYCCNT`:** 1 такт = $\approx 10.42\text{ нс}$ (період переповнення 32-бітного лічильника при 96 МГц становить $\approx 44.74\text{ с}$)
* **Інтерфейс виводу діагностики:** `USART2` (`PA2/PA3`, `115200 8N1`) через ST-LINK VCP / YP-05
* **Комбіновані методи вимірювання:**
  1. Програмні лічильники тактів ядра (`DWT`) для внутрішніх часових інтервалів.
  2. Подієві логи з мітками часу мікроконтролера (`EVT`) для довгих ланцюжків операцій.
  3. Службові піни `GPIO` + логічний аналізатор (PulseView) для зовнішньої апаратної верифікації.
  4. Звіти компілятора/лінкера (`--print-memory-usage`, `.map`, `.su`) та *stack painting* (`0xDEADBEEF`) для контролю пам'яті.

## 2. Перелік вимірюваних метрик

| Код метрики | Назва метрики | Одиниці / Формат | Що саме вимірюється в SmartLock | Спосіб виміру |
| :--- | :--- | :--- | :--- | :--- |
| **M-01** | Час виконання задачі ($T_{\text{task}}$) | `min / avg / max` (мкс) | Тривалість кожного обробника в циклі: `fsm`, `buttons`, `imu` (GY-89), `dht11`, `reed_pir`, `servo`, `camera` (OV7670), `flash_log` (W25Q64), `uart_cli` | `DWT` + службові GPIO |
| **M-02** | Період головного циклу ($T_{\text{loop}}$) | `min / avg / max` (мкс) | Повний час однієї ітерації `while(1)` у холостому та навантаженому режимах | `DWT` |
| **M-03** | Затримка реакції на подію ($L_{\text{event}}$) | `min / avg / max / p99` (мкс) | Час від виникнення події до початку реакції в циклі: кнопка блокування (`PC13`), кодові кнопки (`PA1/4/7/9`), `PIR` (`PA0`), геркон (`PB4`), прийом команди UART | `DWT` (ISR $\rightarrow$ task) + Логічний аналізатор |
| **M-04** | Джитер періодичних задач ($J_{\text{task}}$) | `min / max` відхилення (мкс), гістограма | Відхилення реального інтервалу запуску періодичних задач (опитування IMU, контроль дверей) від заданого періоду $T_{\text{nom}}$ та кількість пропущених запусків (`dt > 2 * T_nom`) | `DWT` |
| **M-05** | Завантаження CPU ($U_{\text{CPU}}$) | `%` (вікно 1000 мс) | Частка часу за секунду, коли задачі виконували реальну роботу (без урахування порожніх перевірок таймерів) | `DWT` |
| **M-06** | Статична пам'ять Flash та RAM | Байти та `%` | Загальне заповнення `FLASH` і `RAM`, розбивка за секціями (`.text`, `.data`, `.bss`), модулями (`*.o`) та найбільшими символами | `-Wl,--print-memory-usage`, `arm-none-eabi-size`, `nm` |
| **M-07** | Використання стека (Static & Peak) | Байти / Запас (байт) | Статичний розмір кадрів функцій (`.su`) та фактичний максимум заповнення стека під час сценарію S3 | `-fstack-usage` + *Stack Painting* (`0xDEADBEEF`) |
| **M-08** | Використання динамічної пам'яті (Heap) | `arena / used / free` (байт) | Пікове виділення та перевірка відсутності витоків після тривалої роботи (якщо використовується `malloc`) | `mallinfo()` |

## 3. Протокол форматів UART-логів (контракт для парсингу)

Усі діагностичні рядки повинні починатися з фіксованого префікса великими літерами та завершуватися `\r\n`. Час прибуття рядка на ПК **не використовується** через буферизацію USB VCP — усі часові мітки формуються всередині STM32.

### 3.1. Банер версії збірки (на старті системи)
Фіксує точний коміт прошивки для прив'язки логів до бінарного файлу:
```text
FW build_git=<short_hash> sysclk_hz=96000000
```
*Приклад:* `FW build_git=a1b2c3d sysclk_hz=96000000`

### 3.2. Статистика часу виконання задач та затримок (`STAT`)
Виводиться за командою `STATS` або після завершення тестового прогону:
```text
STAT name=<task_or_latency_name> n=<count> min_us=<min> avg_us=<avg> max_us=<max>
```
*Приклади:*
```text
STAT name=loop n=45210 min_us=42 avg_us=68 max_us=98400
STAT name=imu n=9000 min_us=210 avg_us=235 max_us=640
STAT name=camera n=15 min_us=33100 avg_us=33450 max_us=34200
STAT name=flash_erase n=5 min_us=45200 avg_us=51000 max_us=68400
STAT name=btn_b1_lat n=40 min_us=18 avg_us=410 max_us=96500
```
*Регулярний вираз для парсингу:* `^STAT name=(\S+) n=(\d+) min_us=(\d+) avg_us=(\d+) max_us=(\d+)$`

### 3.3. Подієві мітки часу (`EVT`)
Використовуються для вимірювання затримок у багатоетапних сценаріях (час `t_us` — безперервний 64-бітний лічильник мікросекунд на базі `DWT` або апаратного таймера 1 МГц):
```text
EVT t_us=<timestamp_us> name=<event_name>
```
*Стандартні імена подій SmartLock:*
* `btn_b1_press` $\rightarrow$ `btn_b1_handled` (реакція на блокування/розблокування)
* `code_key_press` $\rightarrow$ `code_key_handled` (введення коду доступу)
* `pir_trig` $\rightarrow$ `alarm_triggered` (спрацювання датчика руху HC-SR501)
* `capture_start` $\rightarrow$ `capture_done` (захоплення кадру OV7670)
* `flash_wr_start` $\rightarrow$ `flash_wr_done` (запис журналу або кадру у W25Q64)
* `uart_cmd_rx` $\rightarrow$ `uart_cmd_tx` (обробка вхідної команди)

*Приклад:*
```text
EVT t_us=10234567 name=btn_b1_press
EVT t_us=10234610 name=btn_b1_handled
EVT t_us=10235000 name=capture_start
EVT t_us=10268420 name=capture_done
```
*Регулярний вираз для парсингу:* `^EVT t_us=(\d+) name=(\S+)$`

### 3.4. Джитер періодичних задач (`JITTER`)
```text
JITTER name=<task_name> period_us=<nom> min_us=<min_err> max_us=<max_err> missed=<cnt>
```
*Приклад:* `JITTER name=imu period_us=5000 min_us=-12 max_us=93400 missed=18`

### 3.5. Завантаження процесора (`LOAD`)
Виводиться раз на секунду:
```text
LOAD pct=<0..100>
```
*Приклад:* `LOAD pct=14`

### 3.6. Звіт про використання стека та heap (`MEM`)
Виводиться за командою `MEM` до та після виконання тестового сценарію:
```text
STACK reserved=<bytes> used=<bytes> free=<bytes>
HEAP arena=<bytes> used=<bytes> free=<bytes>
```
*Приклад:*
```text
STACK reserved=2048 used=1384 free=664
HEAP arena=0 used=0 free=0
```

## 4. Сценарії тестування для збору метрик

Усі вимірювання виконуються на одній і тій самій збірці прошивки (однаковий `build_git` та частота UART):

1. **S1 — Простій (Idle):** Система увімкнена, подій доступу немає, камера та запис у Flash неактивні, працюють лише базові періодичні опитування та фоновий цикл.
2. **S2 — Номінальний режим (PRD):** Типова робота замка згідно з вимогами PRD: регулярне опитування сенсорів (GY-89, DHT11, геркон), поодинокі натискання кнопок/спрацювання PIR, періодичний запис подій у журнал W25Q64.
3. **S3 — Найгірший випадок (Worst-case):** Одночасне накладання всіх важких операцій: захоплення кадру з OV7670 + стирання сектора / запис у W25Q64 + безперервний потік команд по UART + серія зовнішніх подій (натискання кнопки `PC13` / спрацювання `PIR` щонайменше 30–50 разів у випадкові моменти).
4. **Додаткові стрес-сценарії (п. 6.2 методички):**
   * Відмова пристрою на шині I2C1 (від'єднання сенсора або замикання SDA на GND) — вимірювання часу блокування на `Timeout`.
   * Потік команд по UART без пауз під час захоплення кадру — підрахунок втрачених байтів (`ORE` / переповнення кільцевого буфера).
   * Пошук точки зламу — підвищення частоти опитування сенсорів / частоти команд до порушення дедлайнів PRD.
   * Тривалий прогін у режимі S2 (від 60 хв) — перевірка переповнення 32-бітного `DWT` (кожні ~44.74 с) та стабільності пам'яті.
