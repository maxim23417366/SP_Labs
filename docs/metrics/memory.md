## 2. Стек

### 2.1. Виміряно (stack painting, рядки `STACK` у логах)

| | S1 | S2 | S3 |
|---|---:|---:|---:|
| після старту | 720 Б | 720 Б | 720 Б |
| пік за прогін | 760 Б | 760 Б | 760 Б |
| запас від резерву 4 096 Б | 3 336 Б (81 %) | 3 336 Б (81 %) | 3 336 Б (81 %) |

* Під час роботи (камера, Flash, потік UART, події) стек не перевищує 720 Б. 760 Б з'являється лише
  під час виводу команди `STATS`.
* У `S3_uart_ts.txt` перші 165 рядків записано **до скидання МК** (банер `BUILD` — у рядку 166),
  тому 800 Б звідти до S3 не належать. `parse_uart_logs.py` бере їх у пік, тож правильне значення для S3 — 760 Б.
* Стендова команда ЛР2 `h` (`Bench_Command → dht11_line`) доводила стек до **1 040 Б** при старому
  резерві 1 КБ. Це переповнення, тому в `5774b8a` резерв збільшено до 4 КБ (issue #49). У S1–S3 цю
  команду не викликали.

### 2.2. Статична оцінка (`-fstack-usage`)

Найбільші кадри (`mem/stack_usage.txt`): `dht11_line` 376 Б, `bench_verify` 344 Б, `bench_write` 328 Б,
`frame_store_verify` 296 Б, `SelfTest_Report` 232 Б. Майже всі — діагностичний код ЛР2.

Повна глибина — сума кадрів найглибшого ланцюжка плюс переривання. Кадри функцій поза топ-20 `.su`
взято з прологів у `firmware.elf`.

| Шлях | Статика | Виміряно |
|---|---:|---:|
| старт (`main → App_Init → … → SelfTest_Report → snprintf`) | 744 Б | 720 Б |
| команда `STATS` (`main → … → task_uart → Stats_Print → printf`) | 832 Б | 760 Б |
| команда `h` (`main → … → Bench_Command → dht11_line → … → vsnprintf`) | 1 112 Б | 1 040 Б |
| найгірше + вкладені переривання (DMA пріоритет 15, EXTI пріоритет 0, кадр винятку з FPU 104 Б) | 1 344 Б | — |

Статика скрізь трохи більша за вимір (на 3–9 %): вона враховує гілки `printf` з newlib, які
фактично не виконувались. Найгірший випадок 1 344 Б з резерву 4 096 Б — запас 67 %.

## 3. Heap

| | S1 | S2 (67 хв) | S3 |
|---|---|---|---|
| `HEAP arena / used / free` | 1 468 / 1 468 / 0 | 1 468 / 1 468 / 0 | 1 468 / 1 468 / 0 |

Застосунок `malloc` не викликає. Heap бере лише newlib для буфера `stdout` під час першого `printf`.
Значення не змінюється від старту до кінця прогонів (S2 — понад 1 год, §6.2 п. 6), отже **витоку немає**.

## 4. Висновки

1. **Пам'яті достатньо:** Flash 12,9 %, RAM 40,5 %, стек — запас 67 % навіть у статичному найгіршому випадку.
2. **RAM обмежує камеру:** буфер кадру займає 79 % статичної RAM. QVGA RGB565 (153 600 Б) не
   вміщується в 128 КБ, тому роздільну здатність обмежує пам'ять (контрольне питання 10).
3. **Обмеження super loop (для реєстру):** стек один на всю програму, переповнення ніхто не
   помічає (MPU немає). При резерві 1 КБ стек вийшов за межу (1 040 Б), і це помітили лише за stack
   painting. Найглибший шлях дає діагностичний код, а резерв потрібен для всіх. У FreeRTOS кожна
   задача має свій стек і контроль переповнення, але сумарно стеків знадобиться більше.
   *Гіпотеза для ЛР4:* RAM під стеки зросте.
4. **Перевага super loop:** уся пам'ять статична і видна з map-файлу, heap сталий, один стек.

**Як повторити в ЛР4:** взяти артефакт CI нової збірки (`mem/*.txt`) і рядки `STACK` / `HEAP`
з логів S1–S3 після банера `BUILD`.
