# Інструкція запуску UART-навантаження для сценарію S3 (SmartLock, ЛР3)

Цей документ описує порядок запуску генератора навантаження `scripts/uart_load.py` під час вимірювань сценарію **S3 (найгірший випадок)** та стрес-тесту потоку команд без пауз (методичка §6.2.3), а також подальшу обробку зібраних логів через `scripts/parse_uart_logs.py`.

> **Стендовий прогін S3** пишеться через `scripts/uart_capture.py` з тими самими профілями навантаження (`--load-rate`, `--load-burst`, `--load-profile`) — порт плати один, і запис із рядком `BUILD` та `S3_conditions.md` веде той самий процес (`docs/lab_3/bench-runs.md`). `uart_load.py` — для окремих перевірок UART без запису S3.

---

## 1. Підготовка робочого місця

1. Переконайтеся, що встановлено Python 3.8+.
2. Для роботи з реальним COM-портом плати NUCLEO-F411RE встановіть бібліотеку `pyserial` (для режимів `--dry-run` і `--mock` вона не потрібна):
   ```bash
   pip install pyserial
   ```
3. Закрийте інші термінали, які можуть утримувати COM-порт плати (PuTTY, TeraTerm, Arduino Serial Monitor, CubeIDE Serial Console), оскільки ОС дозволяє відкрити порт лише одній програмі одночасно.

---

## 2. Перевірка скрипта без підключеної плати (`--dry-run` і `--mock`)

Перед стендовим запуском можна перевірити коректність роботи утиліти локально без плати:

* **Перегляд плану команд (`--dry-run`):**
  ```bash
  python scripts/uart_load.py --dry-run --duration 15 --rate 20 --profile mixed
  ```
* **Прогін на вбудованому імітаторі прошивки (`--mock`) із збереженням тестового логу:**
  ```bash
  python scripts/uart_load.py --mock --count 50 --profile mixed --out logs/s3_mock.log
  python scripts/parse_uart_logs.py logs/s3_mock.log
  ```

---

## 3. Визначення COM-порту плати NUCLEO-F411RE

* **Windows (PowerShell):**
  ```powershell
  [System.IO.Ports.SerialPort]::getportnames()
  ```
  Або відкрийте *Диспетчер пристроїв → Порти (COM і LPT)* і знайдіть рядок `STMicroelectronics STLink Virtual COM Port (COMx)`.
* **Linux:**
  ```bash
  ls /dev/ttyACM*
  ```
  Зазвичай це `/dev/ttyACM0`.

Параметри підключення прошивки зафіксовані в `app_config.h`: **`115200` біт/с, `8N1`**.

## 4. Запуск сценарію S3 (номінальне пікове навантаження)

За специфікацією `docs/metrics/metrics-spec.md` (§4, S3) під час прогону мають одночасно відбуватися:
1. Безперервний обмін командами по UART (`PING <n>`, періодичні `MEM` і `MARK <n>`).
2. Натискання кнопки користувача **B1 (`PC13`)** та спрацювання датчиків **PIR (`PA0`) / MPU-6050**.
3. Захоплення кадру з камери **OV7670** та запис подій у зовнішню Flash **W25Q64**.

Запустіть скрипт із кореня репозиторію (замініть `COM3` на свій порт):

```bash
python scripts/uart_load.py --port COM3 --duration 20 --rate 20 --profile mixed --out logs/s3_run1.log
```

Що зробить скрипт автоматично:
* на старті надішле `STATS RESET`, щоб обнулити лічильники попереднього прогону;
* протягом **20 секунд** надсилатиме 20 команд/с (`PING <n>`, кожну 10-ту команду `MEM`, кожну 25-ту `MARK <n>`) і паралельно записуватиме всі рядки телеметрії плати (`EVT`, `LOAD`, `PONG`, `STACK`, `HEAP`) у файл `logs/s3_run1.log`;
* у кінці надішле команду `STATS`, дочекається повного виводу блоку `STATS_BEGIN ... STATS_END` та виведе зведення (кількість відправлених `PING`, отриманих `PONG` і втрачених пакетів).

> **Порада:** під час цих 20 секунд на платі виконайте серію натискань B1 / спрацювань PIR та запустіть захоплення кадру камери (або тримайте логічний аналізатор PulseView підключеним на лінії `PC13`, `PA0`, `VSYNC`, `PB6` для паралельної звірки затримок).

## 5. Стрес-тест потоку команд без пауз (методичка §6.2.3)

Для перевірки межі стійкості приймального кільцевого буфера UART під час блокуючого захоплення кадру OV7670 запустіть скрипт із прапорцем `--burst` (відправка команд підряд без затримок):

```bash
python scripts/uart_load.py --port COM3 --duration 5 --burst --profile ping --out logs/s3_burst.log
```

Критерії оцінки результату:
* у підсумку скрипта перевірте рядок `втрачено PING` (різниця між відправленими `PING` та отриманими `PONG`);
* у кінці збереженого файлу `logs/s3_burst.log` перевірте рядок `UART rx_overrun=... cmd_overflow=...` (якщо `rx_overrun > 0`, зафіксуйте це значення у звіті ЛР3 як межу навантаження в архітектурі Super Loop).

## 6. Обробка зібраних логів парсером (`parse_uart_logs.py`)

Після завершення серії прогонів **S1**, **S2** та **S3** сформуйте зведену таблицю метрик для звіту:

```bash
python scripts/parse_uart_logs.py --s1 logs/s1.log --s2 logs/s2.log --s3 logs/s3_run1.log --md docs/metrics/results_s1_s3.md --csv docs/metrics/results_s1_s3.csv
```
