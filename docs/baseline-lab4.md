# Базова лінія для ЛР4 (ЛР3, M09)

Методичка, розділ 8. Мета документа — у ЛР4 (FreeRTOS) повторити ті самі сценарії тим самим
інструментарієм і порівняти числа з цією таблицею. Усе, що тут описано, використовується **без змін**;
що допустимо змінити — розділ 5.

**Еталонна прошивка ЛР3:** `5774b8a` (S1–S3), `firmware.bin` sha256 `3a949999…cddf24`, артефакт CI
`firmware-5774b8a`. E2E і §6.2 — `f5dc804` (`main` після PR #55). Протоколи: `lab_3/test-scenarios.md`
(S1–S3), `lab_3/e2e-test-cases.md` (E2E), реєстр прогонів — `lab_3/bench-runs.md`.

## 1. Як відтворити сценарії

### 1.1. Збірка і прошивка

```bash
make lab3      # збірка в Docker + перевірки шарів + mem-report + host-тести; має бути «LAB3: PASS git=<хеш>»
make flash     # st-flash --reset write firmware/build/firmware.bin 0x08000000
```

Перед прогоном: порт UART вільний (`screen` / `picocom` закриті), запис стартує **до** скидання МК,
щоб у лог потрапив рядок `BUILD,…,git=<хеш>,…,loop=<superloop|freertos>`.

### 1.2. Підключення

| Що | Пін Nucleo | Канал аналізатора | Навіщо |
|---|---|---|---|
| UART (ST-LINK VCP) | PA2 / PA3 | D6 (TX, необов'язково) | 115200 8N1, команди і лог |
| Кнопка B1 | PC13 (CN7-23) | D1 | фізичний фронт події |
| Вихід PIR | PA0 | D7 | фізичний фронт події |
| `PROBE_REACT` | PB1 (CN10-24) | D0 | момент, коли задача забрала подію |
| `PROBE_CAMERA` | PB2 (CN10-22) | D4 | час захоплення кадру |
| `PROBE_STORAGE` | PB12 (CN10-16) | D5 | час запису кадру у W25Q64 |
| `PROBE_LOOP` | PB0 (CN8-4) | вільний канал | тривалість проходу циклу (у ЛР4 — роботи задачі) |

Аналізатор — fx2lafw, `sigrok-cli` / PulseView, **500 кГц** (крок 2 мкс). Через USB-хаб запис обривається
через ≈ 150–160 с (`bench-runs.md`, «Відомі обмеження»): знімати 2–3 записи по ≈ 150 с або без хаба.

### 1.3. Сценарії

| Сценарій | Команда запису | Дії і тривалість | Результат |
|---|---|---|---|
| S1 — простій | `python3 scripts/uart_capture.py --port <порт> --name S1 --duration 10.5 --plan S1 --char-gap 0 --retries 2` | скинути МК, нічого не робити 10 хв | `docs/metrics/S1_*` |
| S2 — номінальний | `… --name S2 --duration 67 --plan S2 --char-gap 0 --retries 2` | B1 → `LOCKED`, ≥ 60 хв у `LOCKED`: рух, удари, код (`test-scenarios.md` S2) | `docs/metrics/S2_*` |
| S3 — найгірший | `… --name S3 --plan S3 --load-rate 20 --load-profile mixed --char-gap 0 --retries 1` + аналізатор | `LOCKED`, зйомки й записи кадрів, UART 20 Гц, 30 натискань B1 під час довгих операцій, до Ctrl+C | `docs/metrics/S3_*`, `docs/captures/S3*.sr` |
| E2E-01…06 | `… --name E2E-0N` | кроки `e2e-test-cases.md` | `docs/lab_3/logs/24–28, 31` |
| §6.2 UART flood / точка зламу | `… --load-rate 50` і `100` по 40 с + `CAM TEST` на старті | `bench-runs.md`, «Сценарії §6.2» | лог 33 |
| §6.2 тривала робота | S2 (≥ 60 хв) | — | `S2_*` |
| FR-10, FR-13, FR-14 | `… --name FR-NN` | кроки `fr-verification-matrix.md` | логи 27, 29, 30, 32 |

Під час запису: `STATS` / `MEM` — надіслати на плату, `! опис` — мітка `MARK <n>` у лозі,
`# текст` — нотатка у файл. Наприкінці скрипт сам надсилає `STATS` і `MEM`. Умови кожного прогону
дописуються в `<name>_conditions.md`.

### 1.4. Обробка

```bash
python scripts/parse_uart_logs.py --s1 docs/metrics/S1_uart_raw.txt --s2 docs/metrics/S2_uart_raw.txt --s3 docs/metrics/S3_uart_raw.txt --md report.md
make mem-report   # Flash / RAM / .su → firmware/build/mem/*.txt
```

Аналізатор: курсори PulseView на фронтах D1 → D0 (B1) і D7 → D0 (PIR), ширина імпульсів D4 / D5.
Час аналізатора прив'язувати до першого `capture_start` і враховувати розходження годинників
(≈ 6,6 ppm, `metrics/dwt-vs-analyzer.md` §1).

| 1 | E2E-02: `TAMPER` під час зйомки | 1/3 | 3/3 | E2E-02 |
| 1 | тривалість зйомки кадру | 1,3–2,1 с | без змін | S3, `capture_*` |
| 2 | реакція B1, max | 2 137 мс | ≤ 20 мс | S3, DWT + аналізатор |
| 3 | джитер `security`, max | 2 916 мс | ≤ 20 мс | S3, `JITTER` |
| 3 | пропуски `buttons`, за хв | 97 | ≈ 0 | S3, `JITTER` |
| 4 | фронт → ISR, max | 1 043 мкс | без змін (≈ 1 мс) | S3, аналізатор |
| 5 | UART 100 Гц під час `CAM TEST`: `rx_overrun` / `rx_peak` | 1 / 2 048 Б | 0 / < 1 100 Б | §6.2, як лог 33 |
| 6 | RAM під стеки | 4 096 Б (один стек) | ≈ 6–10 КБ (сума стеків задач) | `MEM`, `uxTaskGetStackHighWaterMark` |

## 4. Вимірювальний інструментарій

### 4.1. Команди прошивки (UART 115200 8N1, рядок + Enter)

| Команда | Відповідь | Навіщо |
|---|---|---|
| `VER` | `BUILD,fw=SmartLock,…,git=<хеш>,…` | прив'язка логу до прошивки |
| `STATS` / `STATS RAW` / `STATS RESET` | `STAT`, `JITTER`, `JHIST`, `UART`, `OVR`, `DIAG`, `EVTLOG` / сирі такти / скидання лічильників | швидкодія, джитер, втрати |
| `MEM` | `STACK reserved=… used=… free=…`, `HEAP arena=… used=… free=…` | стек (stack painting) і heap |
| `PING <n>` | `PONG seq=<n>` | навантаження і контроль втрат команд |
| `MARK <n>` | `EVT t_us=… name=mark_<n>` | мітка дії оператора в лозі |
| `CAM TEST` / `CAM LOAD` / `CAM EXPORT` | захоплення / читання кадру з Flash / експорт у UART | довга операція, перевірка кадру |

Без запиту прошивка друкує: `EVT t_us=<мкс> name=<подія>` (64-бітний час DWT), `LOAD pct=<%>` раз на секунду,
рядки журналу `EVT,id=…,t_ms=…,name=<ТИП>,…` і `ENV,…`.

### 4.2. Формати логів

Контракт — `metrics/metrics-spec.md` §3: `BUILD`, `STAT`, `EVT`, `JITTER`, `LOAD`, `STACK` / `HEAP`.
Нові рядки ЛР4 — у §3.7: `STACK task=`, `OSHEAP`, `TASKS`, `TRACE`.
Регулярні вирази там же; парсер M03 на них покладається.

### 4.3. Хост-скрипти

| Скрипт | Що робить |
|---|---|
| `scripts/uart_capture.py` | запис UART: `_uart_raw.txt`, `_uart_ts.txt`, `_conditions.md`; навантаження `--load-rate` / `--load-burst` |
| `scripts/parse_uart_logs.py` | таблиці S1/S2/S3: STAT, пари EVT (p99), JITTER, LOAD, MEM; у ЛР4 — ще TASKS, стеки задач, OSHEAP, TRACE і `--log ЛР3=… --log ЛР4=…` для порівняння поруч (M03) |
| `scripts/uart_load.py` | окреме навантаження UART без запису (`metrics/uart-load-guide.md`) |
| `tools/frame_decode.py` | кадр з `CAM EXPORT` → PNG |
| `scripts/host_checks.py` (`make host-checks`) | усі хостові тести, зокрема тести скриптів |

DWT-мітки подій і статистика задач (I03, I04), службові GPIO `PROBE_*` (I05), stack painting і
`mallinfo()` (I06) — `docs/superloop.md` §3–5.

## 5. Що змінити в ЛР4 і що — ні

* **Без змін:** сценарії й команди запису (розділ 1), формати рядків `metrics-spec.md` §3.1–3.6, імена подій
  `EVT`, піни `PROBE_*` і канали аналізатора, налаштування аналізатора. `parse_uart_logs.py` після M03
  розбирає логи ЛР3 так само, як раніше, а рядки ЛР4 лише додано.
* **Банер:** `loop=freertos` замість `loop=superloop` — так логи ЛР3 і ЛР4 не переплутати.
* **Нове в ЛР4 — лише додавати, не замінювати** (формати — `metrics-spec.md` §3.7): стек кожної задачі —
  `STACK task=<ім'я> reserved=… used=… free=…` у байтах (з `uxTaskGetStackHighWaterMark`), стек переривань —
  `STACK task=MSP …`; heap FreeRTOS — `OSHEAP free=… min_ever_free=… total=…` з `xPortGetFreeHeapSize()` /
  `xPortGetMinimumEverFreeHeapSize()` (рядок newlib `HEAP arena=…` лишається); run-time stats — блок `TASKS`;
  `PROBE_LOOP` — на час роботи обраної задачі.
* Числа ЛР4 класти в ту саму таблицю, що в розділі 2, поруч зі значеннями ЛР3.

Щоб числа ЛР3 і ЛР4 можна було порівнювати, метрики в ЛР4 вимірюються так само, як у ЛР3
(погоджено в рев'ю K01, `rtos-design.md`):

| Метрика | Як у ЛР3 | Що зробити в ЛР4 |
|---|---|---|
| реакція на B1 (`btn_b1_handled`, PB1) | мітка ставиться, коли задача забирає подію від ISR, до антидребезгу (`app_tasks.c`, `take()`) | мітку ставимо там само: одразу після `xQueueReceive` з `qKeys` у задачі `buttons`, до таймера антидребезгу |
| завантаження CPU (`LOAD pct=`) | сума тривалостей задач за вікно 1 с (`sched.c`) | `LOAD pct=` рахуємо так само; `100 − IDLE` з `TASKS` друкуємо поруч для довідки |
| джитер і пропуски (`JITTER`) | `dt − period`; пропуск, якщо `dt > 2 × period` (`note_jitter`) | той самий код одразу після `vTaskDelayUntil` |
| імена `STAT` | `uart`, `mem`, `loop` | `uart` → `cmd` + `logger`, `mem` → `logger`, `loop` → немає (парсер зіставляє сам) |
| час `EVT t_us` | 64-бітний DWT | 64-бітний DWT; розширення старших 32 біт — у tick hook |
| навантаження вимірюванням | друк лише `EVT`, `LOAD`, `STAT` за командою | трасування й автоматичний `TASKS` під час S1–S3 вимкнені прапорцем збірки |
