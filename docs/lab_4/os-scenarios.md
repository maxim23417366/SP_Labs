# Сценарії ЛР4: сценарії ОС і порядок прогонів

Методичка ЛР4: §7.1 (ті самі сценарії), §7.2 (сценарії ОС), §6.2–6.5 (як міряти).

Сценарії ЛР3 у ЛР4 виконуються без змін — тим самим описом, тривалістю, кількістю повторів
і інструментом:

* S1, S2, S3 — `docs/lab_3/test-scenarios.md`;
* E2E-01…06 — `docs/lab_3/e2e-test-cases.md`;
* FR-тести — `docs/lab_3/fr-verification-matrix.md`;
* сценарії меж — `docs/lab_3/bench-runs.md`, «Сценарії §6.2»: довга операція і періодична задача,
  30–50 подій під час довгої операції (виконується в складі S3), UART flood, відмова I²C / сенсора,
  точка зламу, тривала робота ≥ 60 хв (= S2), старт / рестарт, відновлення журналу після перерваного
  запису;
* команди запису, підключення аналізатора й обробка — `docs/baseline-lab4.md` §1;
* формати рядків ЛР4 (`STACK task=`, `OSHEAP`, `TASKS`, `TRACE`) — `docs/metrics/metrics-spec.md` §3.7.

Значення з префіксом `TBD_` — стартові, їх уточнюють під час реалізації збірок сценаріїв.

## 1. Сценарії ОС (§7.2)

Кожен сценарій — окрема збірка прошивки ЛР4 з прапорцем `OS_SCENARIO=<N>`. У звичайній прошивці ЛР4
жоден сценарій не ввімкнений.

Для всіх сценаріїв:
* запис: `python3 scripts/uart_capture.py --port <порт> --name <ім'я логу> --char-gap 0 --retries 2`;
* у кінці скрипт надсилає `STATS` і `MEM` — у ЛР4 це блок `TASKS`, рядки `STACK task=` і `OSHEAP`;
* логи — у `docs/metrics/os/`, записи аналізатора — у `docs/captures/os/`;
* у `<ім'я логу>_conditions.md` — збірка, git-хеш з рядка `BUILD`, дата, дії на стенді.

### 1.1. Інверсія пріоритетів: м'ютекс проти двійкового семафора

| | |
|---|---|
| **Збірка** | Варіант A — `mSpi` як м'ютекс. Варіант B — `mSpi` як двійковий семафор (без успадкування пріоритету). В обох додається задача `hog` з пріоритетом між `camera` (1) і `storage` (3): кожні `TBD_HOG_PERIOD_MS` = 1 000 мс займає CPU на `TBD_HOG_BURST_MS` = 300 мс. Лише в цій збірці `camera` тримає `mSpi` на весь запис кадру; у звичайній прошивці — на сторінку (`docs/rtos-design.md`, §3.2), і вікно для інверсії надто коротке, щоб її побачити |
| **Учасники** | Низький пріоритет: `camera` тримає `mSpi` під час запису кадру у W25Q64 (≈ 0,85 с). Високий: `storage` чекає `mSpi`, щоб записати подію в журнал. Середній: `hog` |
| **Дії** | Режим `LOCKED`, 10 разів викликати `MOTION` перед PIR (кадр і подія пишуться у Flash одночасно), інтервал ≥ 5 с. Окремо для варіантів A і B |
| **Що вимірюємо** | Час очікування `mSpi` задачею `storage` (мітки DWT до і після взяття м'ютекса). Аналізатор: `PROBE_STORAGE` (PB12) — запис кадру, `PROBE_LOOP` (PB0) — робота `hog` |
| **Логи** | `OS-1-mutex`, `OS-1-sem` |
| **Очікування** | A: `storage` чекає не довше, ніж `camera` дописує кадр (≤ 0,85 с); `hog` очікування не подовжує, бо `camera` на час утримання отримує пріоритет `storage`. B: очікування довше на тривалість сплесків `hog`, що припали на утримання |
| **PASS** | Max очікування в B більший, ніж в A, і різницю видно на аналізаторі як роботу `hog` |

### 1.2. Переповнення стека

| | |
|---|---|
| **Збірка** | Стек задачі `env` менший за виміряний high water mark на `TBD_STACK_CUT` = 64 Б. Варіант A — `configCHECK_FOR_STACK_OVERFLOW 2`, варіант B — `0` |
| **Дії** | Прошити, скинути МК, 2 хв нічого не робити (`env` читає DHT11 і BMP180 кожні 2 с). Режим `UNLOCKED` |
| **Що вимірюємо** | Рядок `FATAL stack overflow in env`, час від старту до нього, поведінка після хука. Для B — що відбувається без контролю (зависання, HardFault, зіпсовані рядки, перезапуск) |
| **Логи** | `OS-2-check2`, `OS-2-check0` |
| **Очікування** | A: хук спрацьовує за кілька секунд і називає `env`. B: помилку не видно одразу, наслідки випадкові |
| **PASS** | A — хук спрацював з правильним іменем задачі. B — поведінку записано. Після сценарію — звичайна прошивка, у рядку `LOG,MOUNT,result=…` після скидання `damaged=0` |

### 1.3. Голодування

| | |
|---|---|
| **Збірка** | Задача `busy` з пріоритетом `TBD_BUSY_PRIO` = 5 через `TBD_BUSY_START_S` = 30 с після старту активно чекає прапорця (цикл без блокування) `TBD_BUSY_WINDOW_S` = 10 с; прапорець знімає програмний таймер |
| **Дії** | Прошити, скинути МК, 30 с нічого; у вікні натиснути B1 і надіслати `PING 1`; після вікна — ще 30 с і `STATS` |
| **Що вимірюємо** | Блок `TASKS` (частка `busy`, `IDLE` і нижчих задач), `LOAD pct=` у вікні, `JITTER name=env` і `missed`, коли приходить відповідь на `PING`, `btn_b1_lat` |
| **Логи** | `OS-3-starvation` |
| **Очікування** | У вікні: `busy` займає майже весь CPU, `IDLE` ≈ 0. Не виконуються задачі з нижчим пріоритетом: `fsm` (4), `cmd` і `storage` (3), `env` і `logger` (2), `camera` (1) — UART мовчить, `PING` отримує відповідь лише після вікна. Працюють `Tmr Svc` (7) і `buttons` (6): натискання B1 фіксується (`btn_b1_lat`), але стан замка змінюється лише після вікна, бо голодує `fsm`. `security` (5) має той самий пріоритет, що й `busy`, і ділить з нею CPU по тіках. Після вікна все відновлюється без перезапуску |
| **PASS** | Голодування видно в `TASKS`, у паузі UART і в затримці переходу стану після B1; після вікна прошивка працює далі |

### 1.4. Вичерпання черги

| | |
|---|---|
| **Збірка** | Генератор кладе тестові події в `qFsm` (глибина `TBD_EVQ_LEN` = 8) з частотою `TBD_FLOOD_HZ` = 1 000 Гц протягом 5 с; `fsm` обробляє подію не швидше за `TBD_FSM_COST_MS` = 5 мс. Варіант A — відправка без очікування, варіант B — з тайм-аутом `TBD_SEND_TIMEOUT_MS` = 10 мс |
| **Дії** | Прошити, скинути МК, 10 с нічого (далі генератор вмикається сам), через 30 с — `STATS` |
| **Що вимірюємо** | Скільки подій надіслано, прийнято і відкинуто (рядок генератора) і `EVQ dropped` у `STATS` |
| **Логи** | `OS-4-nowait`, `OS-4-timeout` |
| **Очікування** | A: відправник не блокується, втрати = надіслано − прийнято і збігаються з `EVQ dropped`. B: відправник чекає, втрат менше, але генератор не тримає свою частоту |
| **PASS** | Втрати видно в лічильниках і вони сходяться; прошивка далі реагує на B1 |

### 1.5. Вичерпання heap ОС

| | |
|---|---|
| **Збірка** | Усі об'єкти ОС статичні, тому збірка додає одне динамічне створення після старту (наприклад `xQueueCreate` на `TBD_DYN_BYTES` Б) і зменшує `configTOTAL_HEAP_SIZE`, щоб воно не вдалося. `configUSE_MALLOC_FAILED_HOOK 1` |
| **Дії** | Прошити, скинути МК, 1 хв нічого, `MEM` |
| **Що вимірюємо** | Рядок `FATAL malloc failed`, `OSHEAP free / min_ever_free / total`, поведінка після хука |
| **Логи** | `OS-5-heap` |
| **Очікування** | Хук спрацьовує на динамічному створенні; `OSHEAP` показує, що вільного heap менше за запит |
| **PASS** | Хук спрацював, `OSHEAP` пояснює причину, поведінку після хука записано |

### 1.6. Частота тіку 1000 і 100 Гц

| | |
|---|---|
| **Збірка** | Дві збірки звичайної прошивки ЛР4, що відрізняються лише `configTICK_RATE_HZ` = 1000 і 100. Tick hook ставить службовий пін |
| **Дії** | S3 повністю, як у `test-scenarios.md` (≥ 10 хв, 30 подій, UART 20 Гц, аналізатор), окремо для кожної збірки |
| **Що вимірюємо** | `JITTER name=security` max і `missed`, `btn_b1_lat` max, `LOAD pct=` і частка `IDLE` у `TASKS`, частота й тривалість тіку на аналізаторі, FR-03 (15 с) |
| **Логи** | `OS-6-tick1000`, `OS-6-tick100` |
| **Очікування** | 100 Гц: менше накладних витрат ядра (`IDLE` трохи вища), але роздільна здатність затримок 10 мс — джитер `security` (період 20 мс = 2 тіки) і FR-03 гірші на до ±10 мс. 1000 Гц — навпаки |
| **PASS** | Обидва прогони завершені; різниця в джитері, накладних витратах і `IDLE` записана числами |

## 2. Порядок прогонів

Прошивка тегу `lab3` і прошивка ЛР4 вимірюються на тому самому стенді з однаковими
частотою, налаштуваннями UART і вимірювальним кодом (§7.1). Якщо в ЛР3 щось мірялось інакше —
переміряти ЛР3, а не підганяти ЛР4.

### 2.1. Умови

* Стенд не змінюється, поки не завершено прогони обох прошивок.
* Прошивка `lab3`: `git worktree add ../SP_Labs-lab3 lab3`, у ній `make lab3` → `LAB3: PASS git=fa33f85`.
* Числа ЛР3 у `docs/baseline-lab4.md` §2 зняті на `5774b8a` (S1–S3) і `f5dc804` (E2E, сценарії меж).
  Код прошивки тегу `lab3` збігається з `f5dc804`, але відрізняється від `5774b8a`, а стенд відтоді
  змінився. Тому `lab3` переміряється на цьому стенді повністю, і в порівнянні з ЛР4 беруться нові числа.
* Прошивка ЛР4: поточний `main`, `make lab3` → `LAB3: PASS`. Трасування, автоматичний вивід `TASKS`
  і режим пропуску пікселів камери вимкнені.
* Той самий ПК і USB-порт, порт UART вільний; аналізатор — без USB-хаба або записи частинами ≤ 2 хв
  (у ЛР3 запис через хаб обривався після ≈ 150–160 с).
* Перший рядок кожного логу — `BUILD,…,git=<хеш>,…,loop=superloop` або `loop=freertos`.

### 2.2. Порядок і імена логів

Спершу весь блок на `lab3`, потім той самий блок на ЛР4. S2 — останнім у блоці. Команди запису —
`docs/baseline-lab4.md` §1.3 без змін, відрізняється лише `--name`: суфікс `-lab3` або `-rtos`
(`…` у таблиці), щоб не перезаписати файли ЛР3, і `--end` для `S3-rtos` (§2.3).

| № | Сценарій | Ім'я логу (`--name`) | Примітка |
|---|---|---|---|
| 1 | S1 — простій, 10 хв | `S1-lab3`, `S1-rtos` | |
| 2 | S3 — найгірший, ≥ 10 хв, 30 валідних подій (у його складі — 30–50 подій під час довгої операції) | `S3-lab3`, `S3-rtos` | `--load-rate 20 --load-profile mixed --retries 1`, аналізатор. На ЛР4 у складі S3 додатково: 20 натискань коду під час кількох зйомок поспіль і 10 ударів під час зйомки |
| 3 | E2E-01…06 | `E2E-01-lab3` …, `E2E-01-rtos` … | |
| 4 | FR-10: 5 правильних і 5 неправильних кодів | `FR-10-…` | |
| 5 | FR-13: геркон, кроки з `fr-verification-matrix.md` | `FR-13-…` | |
| 6 | FR-14: тривале перевищення порогу DHT11 (≥ 60 с) | `FR-14-…` | однаковий спосіб нагріву |
| 7 | Відмова DHT11 (як у ЛР3, `docs/lab_3/logs/32_fr14_dht11_fail.txt`) і BMP180 (від'єднати на 30 с) | `FAIL-dht-…`, `FAIL-bmp-…` | |
| 8 | Відмова I²C: зависла шина (SDA → GND на 30 с) і вийнятий GY-521 (30 с) | `FAIL-i2c-…`, `FAIL-gy521-…` | окремими прогонами в стані S1 (`UNLOCKED`, без дій); `JITTER buttons` |
| 9 | UART flood і точка зламу: 50 і 100 Гц по 40 с + `CAM TEST` на старті | `FLOOD50-…`, `FLOOD100-…` | `--load-chunk 25` для обох прошивок |
| 10 | Старт / рестарт, зникнення живлення під час запису | `BOOT-…`, `PWR-…` | як у `bench-runs.md`: старт / рестарт, вимкнення живлення (E2E-06), відновлення журналу після перерваного запису (`z`) |

Скрипт запису не перезаписує наявні файли (`вже існує`). Якщо `FR-13-lab3` чи `FR-14-lab3` уже зняті
раніше на цьому стенді, для прогону взяти `FR-13-lab3-2`, `FR-14-lab3-2` (як `S3_try1` у ЛР3).

Орієнтовно 3,5–4 год на кожну прошивку, з них S2 — понад 1 год (за тривалістю прогонів ЛР3).

### 2.3. Наприкінці S3

Скрипт надсилає `STATS` і `MEM`; для `S3-rtos` запис запускати з `--end STATS,MEM,TASKS`, щоб
наприкінці виконались усі три команди. У лозі ЛР4 мають бути блок `TASKS_BEGIN … TASKS_END`, рядок
`STACK task=` для кожної задачі і `OSHEAP`. Записи аналізатора — `docs/captures/S3-lab3*.sr`
і `docs/captures/S3-rtos*.sr`.

### 2.4. Після кожного прогону

* `<ім'я логу>_conditions.md`: дата, хеш, тривалість, дії на стенді.
* Рядок у `docs/lab_4/bench-runs.md`: сценарій, тривалість, хеш, файли, стан.
* Логи — у `docs/metrics/`, записи аналізатора — у `docs/captures/`.
