## 2. Сценарії ОС (§7.2)

Кожен сценарій — окрема збірка з H05 (`OS_SCENARIO=<N>`; остаточну назву прапорця фіксує H05).
У звичайній прошивці ЛР4 (K05) жоден сценарій не ввімкнений.

Для всіх сценаріїв:
* запис: `python3 scripts/uart_capture.py --port <порт> --name <ім'я з таблиці> --char-gap 0 --retries 2`;
* у кінці скрипт сам надсилає `STATS` і `MEM` (у ЛР4 це ще й блок `TASKS`, рядки `STACK task=` і `OSHEAP`);
* логи — у `docs/metrics/os/`, записи аналізатора — у `docs/captures/os/`;
* у `<ім'я>_conditions.md` — збірка, git-хеш з рядка `BUILD`, дата, що робили руками.

### ОС-1. Інверсія пріоритетів: м'ютекс проти двійкового семафора

| | |
|---|---|
| **Що вмикає збірка** | Варіант A — `mSpi` як м'ютекс (як у `rtos-design.md` §3.2). Варіант B — `mSpi` як двійковий семафор (без успадкування пріоритету). В обох варіантах додається задача-навантаження `hog` із пріоритетом між `camera` (1) і `storage` (3): кожні `TBD_HOG_PERIOD_MS` = 1 000 мс займає CPU на `TBD_HOG_BURST_MS` = 300 мс |
| **Хто з ким** | Низький: `camera` (1) тримає `mSpi` під час запису кадру у W25Q64 (≈ 0,85 с). Високий: `storage` (3) чекає `mSpi`, щоб записати подію в журнал. Середній: `hog` |
| **Дії на стенді** | Режим `LOCKED`, 10 разів викликати `MOTION` перед PIR (кадр пишеться у Flash, подія — у журнал одночасно), інтервал ≥ 5 с. Окремо для варіантів A і B |
| **Що вимірюємо** | Час очікування `mSpi` задачею `storage` (мітки DWT до і після взяття, рядок `STAT` / `EVT`, назву фіксує H05). Аналізатор: `PROBE_STORAGE` (PB12, D5) — запис кадру, `PROBE_LOOP` (PB0) — робота `hog` |
| **Імена логів** | `OS-1-mutex`, `OS-1-sem` |
| **Очікування** | A (м'ютекс): `storage` чекає не довше, ніж `camera` дописує кадр (≤ 0,85 с); `hog` її не подовжує, бо `camera` на час утримання отримує пріоритет `storage`. B (семафор): очікування довше на тривалість сплесків `hog`, що припали на утримання (до +`TBD_HOG_BURST_MS` за кожен сплеск) |
| **PASS** | Max очікування в B більший, ніж в A, і різниця пояснюється роботою `hog` на аналізаторі. У звіті — обидва max і пояснення |

### ОС-2. Переповнення стека

| | |
|---|---|
| **Що вмикає збірка** | Стек однієї задачі (`env`, бо в ній найглибший ланцюжок через драйвери I²C) — менший за виміряний high water mark на `TBD_STACK_CUT` = 64 Б. Варіант A — `configCHECK_FOR_STACK_OVERFLOW 2`, варіант B — `0` |
| **Дії на стенді** | Прошити, скинути МК, нічого не робити 2 хв (`env` читає DHT11 і BMP180 кожні 2 с). Режим `UNLOCKED`, щоб не писати в журнал |
| **Що вимірюємо** | Рядок `FATAL stack overflow in env` з хука; час від старту до нього; поведінка після хука. Для B — що відбувається без контролю (зависання, HardFault, зіпсовані рядки, перезапуск) |
| **Імена логів** | `OS-2-check2`, `OS-2-check0` |
| **Очікування** | A: хук спрацьовує за кілька секунд і називає саме `env`. B: помилка не помічена одразу; наслідки випадкові |
| **PASS** | A — хук спрацював з правильним іменем задачі. B — поведінку записано. Після сценарію — звичайна прошивка; у рядку `LOG,MOUNT,result=…` після скидання `damaged=0` (якщо ні — це теж результат для звіту) |

### ОС-3. Голодування

| | |
|---|---|
| **Що вмикає збірка** | Задача `busy` з пріоритетом `TBD_BUSY_PRIO` = 5 через `TBD_BUSY_START_S` = 30 с після старту активно чекає прапорця (цикл без блокування) протягом `TBD_BUSY_WINDOW_S` = 10 с; прапорець знімає програмний таймер (`Tmr Svc`, 7) |
| **Дії на стенді** | Прошити, скинути МК, 30 с нічого, далі під час вікна натиснути B1 і надіслати `PING 1`, після вікна — ще 30 с і `STATS` |
| **Що вимірюємо** | Блок `TASKS` (частка `busy`, `IDLE` і нижчих задач), `LOAD pct=` у вікні, `JITTER name=env` / `missed`, чи відповідає `PING` і коли, `btn_b1_lat` (`buttons` вища за `busy`) |
| **Імена логів** | `OS-3-starvation` |
| **Очікування** | У вікні: `busy` ≈ 100 % часу, `IDLE` ≈ 0; `env`, `logger`, `cmd`, `camera` не виконуються (UART мовчить, `PING` отримує відповідь лише після вікна); `buttons` і таймери працюють. Після вікна все відновлюється без перезапуску |
| **PASS** | Голодування видно в `TASKS` і в паузі UART; після вікна прошивка працює далі |

### ОС-4. Вичерпання черги

| | |
|---|---|
| **Що вмикає збірка** | Генератор подій (програмний таймер або задача) кладе тестові події в `qFsm` (глибина `TBD_EVQ_LEN` = 8) з частотою `TBD_FLOOD_HZ` = 1 000 Гц протягом 5 с; `fsm` обробляє кожну подію не швидше `TBD_FSM_COST_MS` = 5 мс. Варіант A — `xQueueSend(…, 0)` (як у прошивці), варіант B — тайм-аут `TBD_SEND_TIMEOUT_MS` = 10 мс |
| **Дії на стенді** | Прошити, скинути МК, 10 с нічого, далі генератор вмикається сам; через 30 с — `STATS` |
| **Що вимірюємо** | Скільки подій надіслано, прийнято, відкинуто (рядок генератора, назву фіксує H05) і `EVQ dropped` у `STATS` |
| **Імена логів** | `OS-4-nowait`, `OS-4-timeout` |
| **Очікування** | A: відправник не блокується, втрати = надіслано − прийнято і збігаються з `EVQ dropped`. B: відправник чекає, втрат менше, але генератор не встигає свою частоту |
| **PASS** | Втрати видно в лічильниках і вони сходяться; прошивка далі реагує на B1 |

### ОС-5. Вичерпання heap ОС

| | |
|---|---|
| **Що вмикає збірка** | Усі об'єкти статичні (`rtos-design.md` §1, п. 5), тому збірка додає одне динамічне створення після старту (наприклад `xQueueCreate` на `TBD_DYN_BYTES` Б) і зменшує `configTOTAL_HEAP_SIZE` так, щоб воно не вдалося. `configUSE_MALLOC_FAILED_HOOK 1` |
| **Дії на стенді** | Прошити, скинути МК, 1 хв нічого, `MEM` |
| **Що вимірюємо** | Рядок `FATAL malloc failed` з хука, `OSHEAP free / min_ever_free / total` до і після, поведінка після хука |
| **Імена логів** | `OS-5-heap` |
| **Очікування** | Хук спрацьовує на динамічному створенні; `OSHEAP min_ever_free` ≈ 0 або менше за запит; без хука `xQueueCreate` повернув би `NULL` |
| **PASS** | Хук спрацював, `OSHEAP` пояснює чому; поведінку після хука записано |

### ОС-6. Частота тіку 1000 і 100 Гц

| | |
|---|---|
| **Що вмикає збірка** | Дві збірки звичайної прошивки ЛР4, що відрізняються лише `configTICK_RATE_HZ` = 1000 і 100. Tick hook ставить службовий пін (M02) |
| **Дії на стенді** | S3 повністю, як у `test-scenarios.md` (≥ 10 хв, 30 подій, UART 20 Гц, аналізатор) — окремо для кожної збірки |
| **Що вимірюємо** | `JITTER name=security` max і `missed`, `btn_b1_lat` max, `LOAD pct=` і частка `IDLE` у `TASKS`, частота й тривалість тіку на аналізаторі (пін tick hook), FR-03 (15 с) |
| **Імена логів** | `OS-6-tick1000`, `OS-6-tick100` |
| **Очікування** | 100 Гц: менше накладних витрат ядра (`IDLE` трохи вища), але роздільна здатність затримок 10 мс — джитер `security` (період 20 мс = 2 тіки) і FR-03 гірші на до ±10 мс. 1000 Гц: навпаки |
| **PASS** | Обидва прогони завершені; різниця в джитері, накладних витратах і `IDLE` записана числами |
