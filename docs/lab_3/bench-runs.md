## Запис UART

`scripts/uart_capture.py` — без pyserial, macOS/Linux. Пише три файли з префіксом `--name`:

| Файл | Зміст |
|---|---|
| `<name>_uart_raw.txt` | сирий потік байт без змін — вхід для `scripts/parse_uart_logs.py` |
| `<name>_uart_ts.txt` | кожен рядок із часом ПК, надіслані команди, нотатки й MARK |
| `<name>_conditions.md` | git-хеш з рядка `BUILD`, час, порт, команди, MARK, поля умов для ручного заповнення |

Під час запису з клавіатури: `STATS` / `MEM` / `d` — надіслати на плату; `# текст` — нотатка
лише у файл; `! опис дії` — `MARK <n>` на плату (подія в EVT-лозі) + нотатка з описом.
Наприкінці (за `--duration` або Ctrl+C) скрипт сам надсилає `STATS` і `MEM`. Команди з `--start`
надсилаються після рядка `BUILD` і 3 с self-test. Команда без відповіді після всіх спроб
потрапляє в розділ conditions «Команди без відповіді».

Перед кожним прогоном: плата прошита, `screen`/`picocom` закриті (порт один), запис стартувати
**до** `RESET`, щоб у лог потрапив рядок `BUILD`.

```bash
# S1 — простій 10 хв
python3 scripts/uart_capture.py --port /dev/cu.usbmodem12303 --name S1 --duration 10 --plan S1

# S2 — запустити після переходу в LOCKED, ≥ 60 хв (запас 2 хв)
python3 scripts/uart_capture.py --port /dev/cu.usbmodem12303 --name S2 --duration 62 --plan S2

# S3 — до 30 валідних подій, зупинка Ctrl+C
python3 scripts/uart_capture.py --port /dev/cu.usbmodem12303 --name S3 --plan S3

# пробний прогін (не доказ) — окрема тека
python3 scripts/uart_capture.py --port /dev/cu.usbmodem12303 --name S1_dry --out /tmp/smartlock --duration 2
```

Файли S1–S3 — у `docs/metrics/` (вимога протоколу), запис PulseView S3 — `docs/captures/`.
Логи E2E і §6.2 — `docs/lab_3/logs/` з наступним вільним номером.

## Відомі обмеження, що впливають на прогони

- Прийом UART опитувальний, без переривання і буфера (лог 20): команди одним блоком губляться
  навіть у штатному циклі — 9 з 40 `PING`, а частково прийнята команда виконується зі зміненим
  змістом (`PING 12` → `PING 1`, `'MMARK 2'`). Тому `uart_capture.py` надсилає команди по символу
  з паузою 5 мс, після 0,2 с тиші на лінії, з `\r` попереду, і перевіряє відповідь на `STATS`,
  `MEM`, `PING n`, `MARK n` (до 3 спроб). Так втрат 0 з 81. Команди з `screen`/`picocom`
  захисту не мають — їх результат перевіряти за відповіддю.
  Виправлення (прийом через DMA, issue #41) перевірено на стенді — лог 22: 81/81 і 40/40 без
  обходу, команди під час захоплення кадру не губляться. Після його злиття обхід можна вимкнути.
- ST-LINK VCP зависає на потоці з ПК довшому за ~380 Б, якщо плата одночасно відповідає (лог 22):
  прийом відновлюється лише перепідключенням USB. Для UART flood (§6.2) подавати потік порціями
  ≤ 25 команд або оновити прошивку ST-LINK.
- Під час довгих операцій (запис кадру ~0,85 с, DHT11 ~41 мс) губиться навіть по-символьний
  прийом. Для UART flood і S3 це очікуваний результат, а не збій скрипта.
- Стирання сектора журналу (~64 мс, раз на 128 записів) виконується в тому самому проході, що й запис.
- Self-test дає 2 WARN (MPU-6050 зсув нуля, LSM303D осі X/Y на межі шкали) — на роботу не впливає.
