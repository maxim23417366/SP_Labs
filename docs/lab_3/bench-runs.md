## Запис UART

`scripts/uart_capture.py` — без pyserial, macOS/Linux. Пише три файли з префіксом `--name`:

| Файл | Зміст |
|---|---|
| `<name>_uart_raw.txt` | сирий потік байт без змін — вхід для `scripts/parse_uart_logs.py` |
| `<name>_uart_ts.txt` | кожен рядок із часом ПК, надіслані команди, нотатки й MARK |
| `<name>_conditions.md` | git-хеш з рядка `BUILD`, час, порт, команди, MARK, поля умов для ручного заповнення |

Під час запису з клавіатури: `STATS` / `MEM` / `d` — надіслати на плату; `# текст` — нотатка
лише у файл; `! опис дії` — `MARK <n>` на плату (подія в EVT-лозі) + нотатка з описом.
Наприкінці (за `--duration` або Ctrl+C) скрипт сам надсилає `STATS` і `MEM`. Команди з `--start`
надсилаються після рядка `BUILD` і 3 с self-test. Команда без відповіді після всіх спроб
потрапляє в розділ conditions «Команди без відповіді».

Перед кожним прогоном: плата прошита, `screen`/`picocom` закриті (порт один), запис стартувати
**до** `RESET`, щоб у лог потрапив рядок `BUILD`.

```bash
# S1 — простій 10 хв (так проведено S1: запуск, потім st-flash --reset reset)
python3 scripts/uart_capture.py --port /dev/cu.usbmodem11303 --name S1 --duration 10.5 --plan S1 \
    --char-gap 0 --retries 2

# S2 — від скидання МК; B1 → LOCKED, від LOCKED ≥ 60 хв (запас на підготовку)
python3 scripts/uart_capture.py --port /dev/cu.usbmodem11303 --name S2 --duration 67 --plan S2 \
    --char-gap 0 --retries 2

# S3 — до 30 валідних подій, зупинка Ctrl+C; навантаження UART генерує той самий процес
python3 scripts/uart_capture.py --port /dev/cu.usbmodem11303 --name S3 --plan S3 \
    --load-rate 20 --load-profile mixed --char-gap 0 --retries 1

# пробний прогін (не доказ) — окрема тека
python3 scripts/uart_capture.py --port /dev/cu.usbmodem11303 --name S1_dry --out /tmp/smartlock --duration 2
```

**Навантаження UART у S3.** Порт плати один: `scripts/uart_load.py` (M03) і `uart_capture.py`
одночасно його не відкриють. Тому в S3 навантаження дає сам `uart_capture.py`:
`--load-rate <Гц>` або `--load-burst` (без пауз, методичка §6.2.3), `--load-profile ping|mixed` —
ті самі команди, що в `uart_load.py` (`PING <n>`, кожна 10-та `MEM`, кожна 25-та `MARK <n>`), без
очікування відповіді. Підсумок (надіслано, отримано `PONG`, фактичний темп) — у `S3_conditions.md`;
втрати — за `seq` у сирому лозі (парсер M03). `--char-gap 0 --retries 1` — бо прийом уже через DMA
(лог 22); з обходом `--char-gap 0.005` рядок `PING <n>` іде ≈ 50 мс і 20 Гц недосяжні.
`uart_load.py` лишається для окремих перевірок UART без запису S3 (`docs/metrics/uart-load-guide.md`).

Файли S1–S3 — у `docs/metrics/` (вимога протоколу), запис PulseView S3 — `docs/captures/`.
Логи E2E і §6.2 — `docs/lab_3/logs/` з наступним вільним номером.

## Реєстр прогонів

Стан: `NOT_RUN` — не проведено, `DRY` — пробний, `DONE` — проведено на перевіреній збірці, сирі дані
передано на аналіз (вердикт метрик — за відповідальним за аналіз), `PASS` / `FAIL` — перевірка з
власним критерієм. Номер порту залежить від USB-гнізда — дивитись `ls /dev/cu.usbmodem*`.

## Відомі обмеження, що впливають на прогони

- Прийом UART через DMA (PR #42, перевірено — лог 22): обхід у скрипті не потрібен,
  `--char-gap 0 --retries 1`/`2`. На збірках до PR #42 прийом опитувальний і губить команди
  (лог 20, 9 з 40 `PING`) — тоді `--char-gap 0.005 --retries 3`. Команди з `screen`/`picocom`
  перевіряти за відповіддю.
- ST-LINK VCP зависає на потоці з ПК довшому за ~380 Б, якщо плата одночасно відповідає (лог 22):
  прийом відновлюється лише перепідключенням USB. Для UART flood (§6.2) подавати потік порціями
  ≤ 25 команд або оновити прошивку ST-LINK.
- Під час довгих операцій (зйомка ~1–2 с + запис кадру ~0,85 с, DHT11 ~42 мс) цикл стоїть: команди
  UART завдяки DMA не губляться (лог 22), але відповідь затримується.
- Стирання сектора журналу (~64 мс, раз на 128 записів) виконується в тому самому проході, що й запис.
- Натискання кнопок коду дає `TAMPER` вище порога 200 мг (640–1339 мг; кнопки й MPU-6050 на одній
  основі), а зйомка кадру (~2,3 с) блокує цикл раніше, ніж натискання проходить антидребезг: у
  `LOCKED` код вводиться ненадійно (issue #51). Впливає на FR-10, E2E-03 і крок 5 S2.
  Виправлення — PR #55 (натискання ловить EXTI, тривалість за тактами DWT); `TAMPER` від натискань
  лишається (поріг `TBD_TAMPER_THRESHOLD_MG` — рішення команди), зрідка ще губиться натискання під
  час кількох зйомок поспіль (issue #54).
- Логічний аналізатор fx2lafw через USB-хаб обриває потік через ~150–160 с (1 МГц і 500 кГц, S3):
  довгі записи робити частинами по ≤ 2 хв.
- `JITTER … missed` у S1 = кількості читань DHT11 (313 за 10,5 хв): кожне читання блокує цикл на
  ~42 мс — це не втрати подій.
- Self-test дає 2 WARN (MPU-6050 зсув нуля, LSM303D осі X/Y на межі шкали) — на роботу не впливає.
