# ЛР3 — прийом команд UART через DMA (виправлення втрат RX)

## 1. Дефект

На `main` `fd23599` у штатному циклі без навантаження: з 40 команд `PING n`, надісланих
одним блоком, 9 загублено (`UART rx_overrun=14`). Частково прийнята команда виконувалась
зі зміненим змістом (`PING 12` → `PONG seq=1`), а загублений `\r` склеював команди
(`unknown command 'MMARK 2'`). Докази — `docs/lab_3/logs/20_uart_rx_loss.txt`
(гілка `lab3/bench-capture`).

**Причина.** `Platform_UartGetChar()` опитував регістр USART2 з `task_uart()`. Приймач
STM32F4 тримає один байт (DR) плюс той, що зсувається; при 115200 8N1 символ — 86,8 мкс.
Будь-яка пауза циклу довша за ~174 мкс під потоком дає ORE: security ~1,6 мс кожні
20 мс, env/DHT11 ~41 мс кожні 2 с, блокувальний `printf`. Скидання ORE читанням DR
викидало й останній прийнятий байт.

## 2. Чому DMA, а не переривання RXNE

Переривання RXNE + кільце закрило б паузи циклу, але не вікна з `__disable_irq()`:

| Вікно | Тривалість | Байтів за цей час на 115200 |
|---|---|---|
| зчитування DHT11 (`Platform_Dht11Capture`) | ~5 мс кожні 2 с | ~58 |
| лінія кадру OV7670 (`camera_dvp.c`, `irq_lock_per_line`) | до ~1 мс × 120 ліній | до ~12 на лінію |

Під час такого вікна обробник RXNE не запуститься, а приймач переповниться після
двох байтів. **DMA1 Stream5 / Channel 4 (USART2_RX)** пише кожен байт у пам'ять
апаратно — незалежно від PRIMASK, зайнятості циклу і `printf`.

## 3. Як працює

```
USART2 RX ──DMA1 Stream5 (кільце, CIRC)──► s_buf[2048]      апаратно, без CPU
                     │ HT / TC (пріоритет 15)
                     ▼
              s_halves++  (лише рахує половини кільця)

task_uart() → Platform_UartGetChar() → UartRx_Get():
   W = h·1024 + ((2048 − NDTR − h·1024) mod 2048)   скільки записав DMA
   W − R = 0            → PLATFORM_UART_NONE
   W − R > 2048 − 16    → PLATFORM_UART_LOST (один раз), R = W
   інакше               → s_buf[R++ mod 2048]
```

* `firmware/Platform/uart_rx.c` — логіка кільця, без HAL (тестується на ПК);
* `firmware/Platform/uart_rx_port.h` — регістри DMA1 Stream5 / USART2 CR3.DMAR,
  обробник `DMA1_Stream5_IRQHandler`; у `firmware.ioc` DMA не налаштовано, тож
  CubeMX нічого не перезапише. Якщо колись додати USART2_RX DMA у CubeMX, лінкер
  повідомить про подвійний `DMA1_Stream5_IRQHandler` — тоді прибрати один із них;
* `Platform_IoInit()` запускає прийом (`UartRx_Start()`), після `MX_USART2_UART_Init()`.

**Буфер 2048 Б = 178 мс прийому.** Кільце переповнюється, лише якщо цикл не читає
довше за 178 мс *і* ПК увесь цей час безперервно шле. Найдовша пауза циклу — повний
`STATS` (~0,2 с друку) — під час звичайної роботи терміналу на це не потрапляє.
Половина кільця (1024 Б, 89 мс) — межа, на яку може запізнитися обробник HT/TC; найдовше
вікно `__disable_irq()` — ~5 мс.

## 4. Якщо байти все ж загублено

Втрата не мовчазна і не змінює змісту команди:

* `Platform_UartGetChar()` один раз повертає `PLATFORM_UART_LOST` на місці втрати;
* `task_uart()` → `Cmd_RxLost()`: рядок, що набирався, і все до найближчого `\r` / `\n`
  відкидаються — уламок не виконується як команда (`PING 1` замість `PING 12`) і не
  склеюється з наступною (`MMARK 2`);
* на кінці відкинутого рядка — відповідь `ERR,cmd=dropped,reason=rx_lost`, щоб ПК /
  `scripts/uart_capture.py` міг повторити команду;
* наступна ціла команда виконується нормально.

Якщо втрата припала на межу між командами, відкидається й наступна (повністю
прийнята) команда — початок рядка після втрати неможливо відрізнити від уламка.

## 5. Метрики в STATS

```
UART rx_overrun=<n> cmd_overflow=<n> cmd_dropped=<n> rx_peak=<Б>
```

| Поле | Що означає | Норма |
|---|---|---|
| `rx_overrun` | скільки разів переповнилось кільце DMA (до виправлення — ORE) | 0 |
| `cmd_overflow` | рядків, довших за `CMD_LINE_MAX` (як і раніше) | 0 |
| `cmd_dropped` | рядків, відкинутих через втрату байтів (`ERR,cmd=dropped`) | 0 |
| `rx_peak` | найбільше байтів, що чекали в кільці, з 2048 | запас до 2032 |

`rx_peak` показує, наскільки потік команд наблизився до втрат: блок з 40 `PING n` —
~330 Б (16 %).

## 6. Перевірка

**На ПК** (`make test`):

* `test_uart_rx` (8 тестів) — справжній `uart_rx.c` на моделі DMA1 Stream5
  (`fake_uart_dma.c`): блок 40 команд без читання, багато обертів кільця, замасковані
  переривання через половину і кінець кільця (DHT11 / камера), обробник посеред
  читання, майже повне кільце без втрат, переповнення → один `LOST` і відновлення;
* `test_sched.c` → `test_uart_rx_lost_drops_damaged_line` — три випадки з журналу
  дефекту: `PING 12` без «2», загублений `\r` між `MARK 1` і `MARK 2`, загублений
  початок `PING 12`; у кожному — `ERR,cmd=dropped`, а наступна команда виконується;
* покриття `uart_rx.c` — 100 % рядків і гілок.

**На стенді** — те саме відтворення, що в описі дефекту:

1. Прошити, термінал 115200 8N1 із записом у файл.
2. `STATS RESET`.
3. Вставити в термінал одним блоком 40 рядків `PING 1` … `PING 40` (або
   `scripts/uart_capture.py` без по-символьної затримки 5 мс).
4. Очікувано: 40 рядків `PONG seq=1` … `PONG seq=40` по порядку, жодного
   `ERR,cmd=dropped` / `unknown command`.
5. `STATS` → `UART rx_overrun=0 cmd_overflow=0 cmd_dropped=0 rx_peak=` ≈ 330.
6. Те саме під час `CAM TEST` (камера маскує переривання на лінію) і кілька разів
   поспіль, щоб потрапити на зчитування DHT11 (раз на 2 с) — результат той самий.
7. Для UART flood (методичка §6.2): записати `rx_peak`, `rx_overrun`, `cmd_dropped` у
   таблицю; `rx_overrun > 0` можливий лише якщо потік довший за 178 мс безперервно
   приходить, поки цикл друкує довгу відповідь.

**Ресурси:** RAM +2048 Б (кільце) — з 128 КБ; переривання DMA — два на 2048 прийнятих
байтів, кожне кілька тактів.
