# ЛР3 — host-тести і лог CI (I11)

Усе, що можна перевірити без плати, запускається **однією командою** і дає **один лог** з
підсумком — той самий локально і в CI на кожен pull request. Лог іде в звіт (I12) як
доказ: які тести, скільки, з яким покриттям і на якому коміті пройшли.

## 1. Запуск

```sh
cd SP_Labs                       # клон репозиторію (не ZIP — інакше git=nogit)
make host-checks                 # Docker-образ stm32-builder, ~1 хв
```

Останні рядки при успіху:

```
I11 HOST CHECKS: PASS — 29 наборів Unity / 446 тестів, periph_check, self_test, покриття, tools, python
лог: tests/build/I11_host_checks.log
```

Код виходу 0 — усе пройшло, 1 — хоч одна перевірка впала (і в лозі рядки `FAIL: …`).
`make lab3` (I10) викликає `host-checks` після збірки і `fw-check`.

Без Docker (Linux / WSL з `gcc`, `gcov`, `python3`):
`python3 scripts/host_checks.py --git $(git rev-parse --short HEAD)`.

## 2. Що виконується

`scripts/host_checks.py`, кроки по черзі (падіння одного не зупиняє наступні — у лозі
видно все):

| Крок | Команда | Що перевіряє |
|---|---|---|
| `deps` | `scripts/check_deps.sh` | Devices/ без HAL, App/ без HAL і внутрішніх файлів Platform, Platform/ без App/ |
| `unit` | `make -C tests periph selftest coverage` | `periph_check` (ЛР1, моки HAL), усі 29 наборів Unity, `self_test`, покриття gcov з порогом 90 % рядків |
| `tools` | `make -C tests tools` | кадр із прошивки (C) → UART-лог → `tools/frame_decode.py` → PNG, побайтно з тестовим малюнком |
| `python` | `unittest discover` у `scripts/` і `tools/` | Python-інструменти стенда: розбір UART-логів, навантаження UART, декодер кадру, сам `host_checks.py` |

## 3. Лог `I11_host_checks.log`

```
I11 HOST CHECKS git=<хеш> utc=<час UTC>
  tool: gcc …  / gcov … / Python … / arm-none-eabi-gcc …
==================== I11 крок: deps ====================
$ <команда>
<повний вивід>
… (unit, tools, python)
==================== I11: ПІДСУМОК HOST-ПЕРЕВІРОК ====================
  deps    exit=0   0.0 s           ← код виходу і час кожного кроку
  Unity: 29 наборів, 446 тестів, 0 падінь
    test_bmp180   14 тестів  0 падінь   ← по рядку на набір
    …
  periph_check: 82 перевірок, 0 падінь
  self_test: PASS
  Покриття (рядки):  firmware/Devices 99.88 % …  OK
  tools: frame_decode OK
  python: 20 тестів, OK
I11 HOST CHECKS: PASS — …
```

Підсумок рахує сам скрипт з виводу тестів і **не пропускає** падінь, які легко
проґавити очима: набір з `Failures > 0`; набір, що аварійно завершився без рядка
`N Tests N Failures` (segfault); покриття нижче порогу; `periph_check`, `self_test`,
`frame_decode` чи Python з помилкою. Це перевіряють `scripts/test_host_checks.py`
(8 тестів на зразках виводу).

## 4. Лог з CI

На кожен PR і push у `main` (`.github/workflows/ci.yml`): крок
**Host checks - tests, coverage, tools, python (I11)** і артефакт **`firmware-<хеш>`**.

1. GitHub → **Actions** → запуск потрібного коміту (у назві — повідомлення коміту).
2. Унизу сторінки запуску — **Artifacts** → `firmware-<хеш>` (zip:
   `tests/build/I11_host_checks.log` і прошивка `firmware/build/firmware.{elf,hex,bin,map}`,
   `firmware/build/mem/*.txt`). Артефакт зберігається і тоді, коли крок упав
   (`if: always()`) — з тим, що встигло зібратися.
3. Хеш у першому рядку логу і в назві артефакту — **голова PR** (коміт, видний на
   сторінці PR) або коміт `main`, а не тимчасовий коміт злиття: CI збирає саме його
   (`lab3-build.md` §4). Цей хеш і наводити у звіті.
4. **Куди покласти лог для звіту:** `docs/lab_3/logs/I11_host_checks_<хеш>.log` — файл
   `I11_host_checks.log` з артефакту без змін, `<хеш>` — з назви артефакту і першого
   рядка логу (`I11 HOST CHECKS git=<хеш>`). Лише лог з CI, не з локального запуску.

## 6. Чого host-тести НЕ доводять

Host-тести працюють на моделях заліза (`tests/doubles/`): вони доводять логіку, формати,
обробку помилок і інтеграцію модулів, але не електричні сигнали і не реальні часи.
Це перевіряється на стенді (H14, `docs/camera.md` §7, `docs/lab_3/lab3-build.md` §5):

* реальні частоти й таймінги (PCLK, VSYNC, EXTI-латентність, `LOAD`, `STAT`);
* реальний кадр OV7670 (експозиція, колір — FR-07);
* стійкість шини I2C / SPI до завад і гарячого підключення;
* тривала робота > 1 год (модель у `test_firmware` — лише логіка часу і черг).

## 7. Відомі недоліки, що впливають на S1–S3

Це Done-критерій I11: що на **цій** прошивці погіршить або зіпсує вимірювання S1–S3
(`test-scenarios.md`, `metrics-spec.md` §4), щоб у звіті (I12) вони не виглядали
несподіванкою. Розділ стоїть тут, поруч із §6: host-тести цього не ловлять — вони
працюють на моделях часу. Позначки: **[стенд]** — число з логу `docs/lab_3/logs/`,
**[оцінка]** — з коду / розрахунку, на стенді на цій збірці не виміряно. Логи 21 і 23
зняті на `3b9df18` і `1c2da0a` — до фіксу камери та I10.

1. **Тривога зупиняє Super Loop на ≈ 2–3 с.** Задача `camera` в одному проході знімає
   кадр і пише його у W25Q64 (`App/camera.c:67`, `:85`): захоплення 1,06–2,10 с, запис
   0,83–0,86 с; MOTION → PHOTO 2,85 с **[стенд: лог 21 рядки 59–83, лог 23 рядки 31–50]**.
   Увесь цей час не опитуються кнопки, PIR, MPU, журнал, UART. `docs/tasks.md` §4
   описує запис кадру окремим проходом (k+2) — у коді він у тому самому. *Де:* S2 п. 2–3
   (PIR / TAMPER у `LOCKED`), S3 — кожна подія. *Зачепить:* `STAT name=loop max`,
   `JITTER … missed`, затримку реакції на події під час кадру; FR-05/06 (повторні
   події), FR-09/10 (код одразу після тривоги), FR-12.
2. **Кнопки коду опитуються, а не через EXTI** (`App/sl_buttons.c:134`, період 10 мс —
   `App/app_config.h:22`): натискання, коротше за блокування з п. 1, губиться повністю.
   B1, PIR і MPU_INT ловить EXTI, але зберігається лише перший фронт, наступні — тільки
   лічильник `OVR name=…` (`Platform/platform_io.c:298`) **[оцінка]**. *Де:* S2 п. 4–5,
   S3 (30 подій під час довгих операцій). *Зачепить:* FR-02, FR-09, FR-10.
3. **`printf` блокувальний:** кожен символ — `HAL_UART_Transmit` (`Platform/retarget.c:18`),
   86,8 мкс на байт при 115200 8N1. `STATS` — 45 рядків, 2294 Б ≈ 0,2 с (модель
   `test_firmware` з нульовими лічильниками; з реальними числами довше), з них 7 рядків
   `DIAG` ≈ 0,48 КБ ≈ 41 мс; `ENV,…` ≈ 46 Б ≈ 4 мс раз на 2 с; `EVT,…` ≈ 4 мс на подію;
   `CAM,photo,…` ≈ 8 мс **[оцінка]**. Стендова команда `c` блокує ≈ 1 с
   (`STAT name=uart max_us=1005539`) **[стенд: лог 21 рядок 32]**. *Де:* S1 (лише
   фінальний `STATS`), S2/S3 — кожна команда і подія; `uart_load.py` (`MEM`, `STATS`).
   *Зачепить:* `STAT name=uart`, джитер `buttons` (10 мс), FR-12.
4. **Запас стека 104 Б** з 1024 (`STACK reserved=1024 used=920 free=104`)
   **[стенд: лог 21 рядок 30, лог 23 рядок 22 — збірки до фіксу камери та I10]**.
   На цій збірці не переміряно; найбільший кадр за `.su` — `dht11_line`, 376 Б
   (`lab3-build.md` §3). *Де:* S3 (найглибший шлях: тривога + журнал + `printf`);
   переповнення стека зіпсує будь-яку FR. Записати `STACK` після старту і `MEM` в кінці
   кожного прогону.
5. **Камера, що зникла після успішної ініціалізації, не переініціалізується.**
   `s_ready` ставиться один раз (`App/cam_test.c:74`) і скидається лише в
   `CamTest_Reset()` (`:419–421`), яку викликають тільки тести. Камера, якої не було
   при старті, ініціалізується повторно при кожному запиті (`:131`, `:167`, `:217`):
   NACK коштує ≈ 0,1 мс **[стенд: лог 13, `i2c_absent`]**, а перший кадр після появи —
   `aec=settling` (може бути пересвічений). Після скидання самої камери (живлення) її
   регістри заводські, і кожна тривога до RESET МК — `capture_err`; одна невдала спроба
   тримає цикл до 1,5 с на фронт VSYNC, за безперервних завад — до 3 × 1,5 = 4,5 с
   (`Platform/camera_dvp.c:65–69`, `App/app_config.h:47`) **[оцінка]**. *Де:* S2/S3 при
   відмові камери, стрес-сценарій §6.2 «відмова пристрою». *Зачепить:* FR-07.
6. **Стирання W25Q64 — у тому самому проході, що й запис.** Журнал: кожен 128-й запис
   стирає сектор, +63,4–64,0 мс (до 400 мс за datasheet) (`App/storage.c:204–212`,
   `flash-layout.md` §3.3) **[стенд: лог 14]**. Кадр: 10 секторів + 150 сторінок ≈
   0,83–0,86 с (входить у п. 1), за datasheet найгірше ≈ 4,55 с (`flash-layout.md`,
   таблиця часу кадру) **[стенд: логи 21, 23]**. *Де:* S2 (запис журналу), S3 (Flash —
   складова навантаження). *Зачепить:* `STAT name=storage max`, джитер; FR-08.
7. **DHT11 і BMP180 читаються блокувально в одному проході `env` раз на 2 с**
   (`App/sl_env.c:139`, `:147`; `App/app_config.h:24`): DHT11 24,1–25,0 мс (з них
   `HAL_Delay(20)` — `Platform/platform_io.c:143`), BMP180 12,0–12,5 мс
   **[стенд: лог 13]** (не ≈ 10 мс, як у коментарі `sl_env.c:147`); разом з рядком `ENV`
   ≈ 40 мс на прохід **[оцінка]**. При відмові: DHT11 20,6–21,2 мс, зависла I²C —
   25,7–26,0 мс на звернення **[стенд: лог 15, `driver-audit.md` §2]**. *Де:* S1, S2, S3
   (фон), §6.2 «відмова I²C». *Зачепить:* `STAT name=env`, `JITTER name=buttons`,
   FR-14/15.
8. **`Platform_Millis()` відстає під час маскування переривань.** Камера вимикає
   переривання на кожен рядок (`Platform/camera_dvp.c:172–174`,
   `CAMERA_IRQ_LOCK_PER_LINE = 1`), а рядок на стенді ≈ 1,71 мс **[стенд: лог 21
   рядок 36]** — довше за 1 мс, тобто частина тиків SysTick губиться
   (`docs/camera.md` §3, «Маскування переривань»): до ≈ 0,7 мс на рядок, ≈ 85 мс на кадр
   **[оцінка]**. DHT11 маскує ~4–5 мс (`Platform/platform_io.c:145–171`) — до ≈ 4 мс на
   читання, до ≈ 30 мс за 15 с EXIT_DELAY **[оцінка]**. Від `Platform_Millis()` рахує FSM
   (`App/app_tasks.c:65`), антидребезг, `t_ms` журналу. B1 → LOCKED = 15,000 с
   **[стенд: лог 21 рядок 80]** виміряно тим самим годинником, тож відставання не видно.
   *Де:* S2 (FR-03 на старті прогону), S3 (розходження `t_ms` і `t_us` у `EVT`).
   *Зачепить:* FR-03 (15 с ± 0,1 с) — перевіряти PulseView (PC13 → ШІМ серво).
9. **Під час `CAM EXPORT` (≈ 10,6 с) кадр тривоги відхиляється:** `CamTest_FrameLocked()`
   (`App/camera.c:31`) → `PHOTO_ERR arg=1`, 2 з 2 **[стенд: лог 23 рядки 36–52]**;
   подія `MOTION` записується. *Де:* S3, якщо експорт узято як довгу операцію.
   *Зачепить:* FR-07.
10. **Прийом UART під довгим блокуванням.** Кільце DMA 2048 Б = 178 мс безперервного
    потоку (`docs/lab_3/uart-rx.md` §3); за 2,85 с з п. 1 воно переповниться, якщо ПК
    шле в середньому > ≈ 0,7 КБ/с. `uart_load.py --rate 20` (≈ 0,2 КБ/с) — вміщується,
    `--burst` — очікувано `rx_overrun > 0` **[оцінка]**. Окремо: ST-LINK VCP перестає
    приймати при потоці ≥ 450 Б з одночасною відповіддю плати — обмеження стенда
    **[стенд: лог 22, лише в незлитому PR #40]**. *Де:* S3, §6.2.3 (UART без пауз).
    *Зачепить:* FR-12.
11. **Перший знімок одразу після скидання МК:** 1 з 20 — `href_timeout` **[стенд: лог 23
    рядки 18, 88]**, до того, як камеру стали ініціалізувати в `App_Init`; на цій збірці
    не переперевірено. *Де:* S2/S3, якщо тривога одразу після RESET. *Зачепить:* FR-07.

Не підтвердилось / не внесено: «камера, якої не було при старті, не
переініціалізується» — переініціалізується при кожному запиті (п. 5); «BMP180 ≈ 10 мс» —
на стенді 12,0–12,5 мс (п. 7).
